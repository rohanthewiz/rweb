## N-051: text helpers send charset=utf-8 (`9d1acfd`)

**The defect.** The doc comments on `WriteHTML`, `WriteText`, `WriteHTMLBytes`
and `WriteTextBytes` promised `charset=utf-8`, but they sent the bare
`consts.MIMEHTML` and `MIMETextPlain`. `rweb.HTML`, `Text`, `CSS` and `JS` sent
bare literals too. A page with no BOM and no `<meta charset>` was then decoded
by the browser's locale default (windows-1252 in most), so "café" from a Go
string showed as "cafÃ©".

**Constants** (`consts/mime.go`):
- New `CharsetUTF8 = "charset=utf-8"` and the full header values built from it:
  `MIMEHTMLUTF8`, `MIMETextPlainUTF8`, `MIMECSSUTF8`, `MIMEJavaScriptUTF8`,
  `MIMECSVUTF8`.
- New bare media types `MIMECSS`, `MIMEJavaScript` (RFC 9239) and `MIMECSV`.
- The existing bare constants keep their values, as the plan required:
  `setFileHeaders` appends the charset to them itself, and
  `middleware/critical` matches `"text/html"` with `strings.Contains`.
- The comment block says why there is a charset, why the bare constants stay
  bare, and why JSON and XML have no UTF-8 form.

**Helpers:**
- `Response.go`: the four write methods use `MIMEHTMLUTF8` and
  `MIMETextPlainUTF8`. The `WriteHTML` comment says how to send another
  encoding: set `Content-Type` and write with `WriteString` or `Write`, which
  leave the header alone; a later `WriteHTML` replaces it.
- `Context.go`: the interface comments now name the full header value. The
  method comments already did.
- `send.go`: `rweb.HTML`, `Text`, `CSS`, `JS` use the UTF-8 constants.
  `setFileHeaders` uses `MIMECSS`, `MIMEJavaScript`, `MIMECSV` and
  `CharsetUTF8` in place of its literals, so the disk and helper paths share
  one source for each type.
- The default error page (`defaultErrorHandler`) writes with `WriteHTML`, so it
  gains the charset with no change of its own.

**Judgement calls beyond the plan:**
- **`rweb.CSV` included.** The plan listed HTML, Text, CSS and JS. CSV has the
  same shape (a `text/*` type written from a Go string), and `setFileHeaders`
  already served `.csv` files as `text/csv; charset=utf-8`.
- **JSON and XML left bare.** RFC 8259 §11 defines no charset parameter for
  `application/json`. On `application/xml` a charset parameter would override
  the document's own encoding declaration (RFC 7303 §3.2), and without one
  XML's own rules already default to UTF-8. `setFileHeaders` still sends
  `charset=utf-8` on `.json`, `.map` and `.xml` files; that was not changed.

**Behaviour change:** the header charset now outranks a `<meta charset>` in the
page (only a BOM beats it). An app that wrote non-UTF-8 HTML through
`WriteHTML` and relied on a meta tag would now be decoded as UTF-8. Noted in
SKILL.md.

**Tests:**
- New `text_charset_test.go`, run against a real listener with
  `Serve`/`Shutdown`:
  - `TestTextHelpersSendUTF8Charset`: all nine helpers send one Content-Type
    with the exact constant, `mime.ParseMediaType` reads `charset=utf-8`, and
    a non-ASCII body ("café ✓") arrives byte for byte.
  - `TestJSONAndXMLStayWithoutCharset`: `WriteJSON`, `rweb.JSON` and
    `rweb.XML` stay bare.
  - `TestTextCharsetHandlerOverride`: a handler's own
    `text/html; charset=iso-8859-1` with `WriteString` survives; the same
    header followed by `WriteHTML` is replaced, leaving one line.
  - `TestDefaultErrorPageHasCharset`.
- Updated expectations: `TestContentTypes` (`send_test.go`),
  `TestWriteHTMLBytes` and `TestWriteTextBytes` (`Response_test.go`).

**Docs:** a paragraph in SKILL.md after the header-case paragraph (response
